## Functional scope

A manager selects actual, verified human-submitted evidence versions. The engagement selector reads paginated tenant records through `GET /v1/evidence-packs/options/engagements`, showing each title and pinned library. The BFF checks live manager authority before and after the read. Unscoped preparation uses the current published library; if none exists, the UI requires an actual engagement with its recorded library. Loading/error states disable preparation, refresh is explicit, and scope changes clear the preparation acknowledgement. The server checks their exact provider bytes and retention before preparing an immutable pack. The database selects the applicable control library, checks tenant/engagement/control references, records the selected receipt identities and persists the exact UTF-8 manifest text plus its SHA-256. The serialization identifier is `postgres-jsonb-text-v1`: consumers retain those exact bytes, rather than attempting to reproduce PostgreSQL JSON formatting in another language.

Only a current tenant founder who is also an Axiom-internal user can approve or reject the displayed content digest. Both authority records are locked for the transaction. The immutable review captures the actual human's name, actor ID, decision, timestamp, note and reviewed digest. A rejection requires a nonblank reason; a changed document needs a new revision. Approval is separate from artifact retention and publication.

The creator or authorized internal founder explicitly starts archive construction. The server rereads the exact member versions, builds a deterministic stored ZIP, commits a durable build intent, uploads actual bytes and settles only after matching provider readback. The archive receipt is separate from ordinary downloadable evidence. A pending operation can discover and verify an existing exact version without a second PUT. If no object was uploaded, reconciliation remains pending and says that it cannot create one.

Founder release binds the reviewed content hash and the retained archive hash. The content endpoint checks current authorization and recorded publication before and after reading storage, verifies exact version, metadata, retention, size and SHA-256, and returns those stored bytes. The browser independently bounds and hashes the response before offering a download. A released structured JSON report is labelled as such; it is not presented as a retained PDF or ZIP.

## Authority and honest output

The old report RPC signatures without an expected digest are removed. Direct ordinary report INSERT/UPDATE/DELETE/TRUNCATE is denied; a sanctioned draft-create function records exact content, actor and digest. Synthetic seed writers create explicitly labelled, unreviewed drafts without invented storage locations, publication or approvals. Historical rows receive no manufactured review digest or retention receipt.

Drafts are visible only to their authorized creator and live internal tenant founder, in both database policies and BFF reads. Other permitted tenant readers see published reports. Private build requests, storage locations and raw receipts are excluded from authenticated column grants and public HTTP projections. Report and pack mutations are bounded to 64 KiB before idempotency hashing. Founder authority is rechecked before cached mutation responses can be replayed.

The reports page uses actual paginated records, collapsible pack preparation, named engagement/library selection, evidence selection, exact-content preview, immutable review attribution, pending/refusal states and role-appropriate actions. Storage failures have readable user-facing explanations. It removes sample reports, invented scores, random signatures, fabricated filing forms and working-looking client export buttons. Metadata or selection changes revoke preparation acknowledgement. Query failures remain errors rather than empty lists; an interrupted mutation is reported as uncertain. The prior successful-download message is cleared before another attempt.

## Artifact contract and independent verification

`@axiom/report-kit` starts the shared browser-safe schema and branding contract: Axiom Proof, Axiom Minds Private Limited, company URL, generator/version, human review attribution, evidence references and limitations. Node archive construction is a separate export. Initial adoption covers evidence packs; the remaining consumers are listed below.

Bounds are 20 members, 8 MiB per member, 48 MiB aggregate payload, 256 KiB per metadata artifact and 64 MiB finished archive. Stored ZIP entry order, timestamps and permissions are deterministic; paths derive from validated evidence UUIDs and user filenames remain data. Global work capacity, byte limits and request deadlines bound construction and retrieval. No provider location is included in the public manifest.

The Python verifier must come from a separately trusted installation. It requires an independently obtained released archive hash; an optional separately obtained manifest hash adds the exact reviewed-content comparison. It snapshots bounded regular-file bytes, checks the outer digest before parsing, bounds the ZIP directory, and refuses unsupported compression/ZIP64/multipart/comment forms, duplicates, traversal, symlinks, overlap, undeclared files, malformed metadata and member hash/size mismatches. It neither extracts nor executes content. A bundled verifier copy is convenience data, not its own trust anchor. SHA-256 integrity is not called a public-key signature or proof that source assertions are true.

See [the report-kit contract and CLI instructions](../../packages/report-kit/README.md).
