Reviewed upstream: staging `0edceda`, Revision 48, exact CI [35707610075](https://github.com/vikashkaruna/Proof/actions/runs/35707610075) green with 17 applicable jobs and eight verified artifacts. No intervening other-model changes were present. The overall goal remains incomplete.

## Findings and implementation

- **The controller transport could not span service identities.** An explicit HTTPS listener and scheduler client now carry the same opaque protocol as the Unix socket. The controller checks a signed scheduler identity before collecting the body or touching backend state. The default public BFF does not expose this listener. Direct TLS and explicitly trusted platform termination are separate configuration choices.
- **Forwarded identity or public BFF ingress would not authenticate the scheduler.** The verifier pins Google's issuer, one exact audience, immutable service-account subject, verified email and bounded lifetime. It refuses token-selected keys, wrong algorithms, ambiguous audiences and mismatched authorized-party claims. Keys come from one fixed HTTPS endpoint with bounded response/time/cache and no redirect or stale-cache fallback. Duplicate authorization headers, cookies and forwarded-only identity are refused. Account recreation with the same email does not inherit access because the subject is independently pinned.
- **Long-lived backend keys must not be given to Temporal.** The remote client obtains an in-memory ID token only from the assigned workload metadata endpoint. It has no credential-file, proxy, redirect, endpoint-environment or CLI fallback. The explicit remote worker mode only polls the opaque queue and composes with the durable outbox pump. Local and remote modes are mutually exclusive. The legacy queue remains separate.
- **Identity expiry and late responses must preserve execution guards.** Both server transports share one bounded protocol implementation. Authentication precedes body collection, and expiry/disconnect abort the request without releasing the operation slot before backend work settles. Scheduling submission, SQL confirmation and process cleanup remain distinct observations. Cancellation does not prove rollback or permit a fresh claim.
- **Unknown/private input could otherwise cross the transport before rejection.** Both clients now validate outbound run/reconcile/poll/ack schemas before identity lookup or transmission. The shared contract rejects extra fields and changed workflow bindings. Tokens and private transport failures are sanitized outside exception handlers before Temporal serialization.
- **Local ledger tests could be reused after a SQL-only change.** Turbo's package test inputs omitted the root migrations consumed by the ledger enum test. The types test now explicitly includes all SQL migration files. A dry-run inventory confirms all migration inputs, and direct ledger tests pass.

The chosen ID-token audience/header and metadata flow follow Google's [service-to-service documentation](https://docs.cloud.google.com/run/docs/authenticating/service-to-service). The principal/lifetime checks follow the documented [service-account ID-token claims](https://docs.cloud.google.com/docs/authentication/token-types#service_account_id_tokens). Application verification is independent of forwarded headers; Google-signed bearer identity is not connector authorization or immediate revocation.
