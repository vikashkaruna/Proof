## Authority and persistence

Migrations 0050–0051 add two private immutable review tables alongside `controller_security.credentials`. The non-login, non-inheriting `axiom_controller_issuer` role can call only three private issuance/status/revocation functions; it has no table grants, public mutation RPC, application approval authority, usable runtime membership or login provisioned by the migration. No authenticator, controller, worker, SPIRE or service-role grant is added. Existing tenant/RLS/approval/execution/ledger boundaries remain unchanged.

The CLI is manually invoked infrastructure administration. Its external operator reviews exact request/configuration/source hashes. `approvalReference` is a change-record reference, not cryptographic proof of human approval. This tool must never substitute for application signed scope-bound approval, dry-run and validated rollback. Root, database administration and the external HS256 signing operator remain trusted; HS256 possession is inherently broad signing authority. This authority must stay outside the runner and public API.

Issue requests bind a nonzero UUID subject, tenant, reviewed configuration, change reference, exact issuance/expiry and optional predecessor. TTL is 300–3600 seconds; fresh issues must be recent, have at least 60 seconds left and cannot use a future issuance time. The raw UTF8 bytes and SHA-256 are persisted together. Unknown or duplicate fields, changed replay, foreign/unreviewed/revoked/expired predecessors and competing successor branches fail. Credential and immutable review insertion share a transaction. Per-subject advisory locks and predecessor row locks serialize concurrent operations; a failed successor leaves no orphan credential.

Reviewed credentials cannot be retargeted, extended, deleted or unrevoked by ordinary SQL updates. Reviewed revocation preserves its own immutable request and the original issuance. Exact replay returns the same metadata; expired or revoked issue replay never remints authority. Legacy manually provisioned records are preserved unchanged and gain no fabricated review. One successor per predecessor is deliberate: if a prepared successor is abandoned or expires, investigate and explicitly review a fresh initial lineage rather than silently replacing that reviewed relationship.

## Protected output and transport

The stdlib CLI requires isolated Python, protected canonical files/ancestry and a bounded private libpq service. No token or signing/database secret appears in subprocess arguments, SQL, environment, output or error text. The subprocess environment is fixed, without ambient libpq settings. The service requires TCP and `sslmode=verify-full`; separate hash-bound database/backend CA files verify hostname and trust. `PGGSSENCMODE=disable` forces TLS rather than GSS negotiation. PostgreSQL documents that Unix sockets ignore `sslmode` and GSS can otherwise take precedence; the CLI excludes both bypasses. [Official libpq connection documentation](https://www.postgresql.org/docs/current/libpq-connect.html).

The CLI checks the anonymous gateway JWT against the protected signer and produces only the existing Revision 72 JSON contract with fixed controller-role, subject, tenant and time claims. A fresh private directory durably records request, candidate and intent before registry mutation. Successful issuance then verifies the real HTTPS tenant RPC, rechecks current registry status and protected inputs, renames the candidate and writes a ready receipt last. Response sizes and subprocess/socket/whole-network-operation deadlines are bounded. Redirects and ambient proxies are refused. Database, TLS, file or backend uncertainty never triggers automatic retry.

Explicit resume requires the same request/configuration/credential bytes and complete preparation under a nonblocking output lock. It reconciles committed-but-unacknowledged registry changes and the rename/ready crash window. Altered, partial or extra files are preserved and refused. A ready receipt is point-in-time evidence only. Live backend requests still check registry tenant, expiry and revocation; an already-running statement can finish after retirement. Existing uncertain dispatch/journal recovery stays authoritative.

See the [operator contract](../../infra/credential-issuer/README.md) for exact input fields, modes and procedures. Only `backend.key` enters the separate reviewed file-delivery operation; private candidates/receipts are not CI artifacts. Revocation needs no signing-key/API-key read. No host generation, Docker service, cloud resource or secret version is changed by the issuer.
