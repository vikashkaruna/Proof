# Revision 97 — The standing-policy engine (W6.2 · M4.1)

## Scope and assumptions

This slice gives `standing_approval_policies` and `policy_evaluations` (created by 0065) their lifecycle and their consumer — the W6 piece that issues scoped approval tokens through the existing gate or escalates. Operator input was not received. The assumptions are:

1. **A policy changes WHO approved, never WHAT must be true.** A within-scope evaluation issues its token THROUGH `issue_reviewed_plan_approval` (migration 0028) — the plan-version check, the dry-run/rollback freshness gate (BR-2), the digest over the reviewed content and the atomic `approval.token.issued` ledger entry all run exactly as an interactive approval. The policy's named approver (`approved_by`) signs on the token and in the ledger detail; the token's `conditions` carry `standing_policy_id` and `standing_policy_version`, so every execution traceable to a policy names it and its version.
2. **Dual control as a schema fact.** A new constraint `standing_policies_dual_control` requires `created_by <> approved_by`; `create_standing_policy` refuses a self-approved policy (`dual_control_required`) before the database has to. A policy is immutable: a changed scope is a new policy with a fresh dual control, and revocation is the off switch.
3. **Scope is closed.** Only the three keys the engine reads (`action_types`, `max_actions`, `environments`) are accepted — enforced in the BFF zod schema (`.strict()`) and by `standing_policy_scope_is_valid` in the database. An unknown key that today would be ignored is a grant nobody vetted the day the engine grows a reader for it.
4. **Escalation is a decision, not an error.** A scope miss (any action type outside the policy's `action_types`) or an oversize batch (`max_actions`) records a `policy_evaluations` row with decision `escalated` and ledgeres `monitoring.policy.escalated` (agent `nazar`, consistent with the scheduler) — a human must look, and the ordinary approve route is the human path. The BFF renders escalation as 200 with `decision: 'escalated'` and the uncovered types.
5. **Gate refusals are not policy decisions.** If `issue_reviewed_plan_approval` refuses under the locks (`actions_not_ready`, `actions_in_flight`, `content_changed`, `plan_changed`, …), the evaluation returns that decision verbatim and records NO `policy_evaluations` row — the policy made no authority decision here.
6. **A lapsed policy retires itself.** Evaluation compares `expires_at` to `clock_timestamp()` (the same freshness convention as the dry-run TTL in `issue_plan_approval` — `now()` would be frozen inside a long transaction), flips a lapsed-but-still-active policy to `expired`, and records the evaluation. `revoke_standing_policy` is immediate, once, and ledgered.
7. Evaluation locks in the established order (plan, then policy, then actions inside the issuance) so an evaluation can never interleave with an approval or a claim.

## Change

- **Migration 0068** — ledger values `monitoring.policy.registered`, `monitoring.policy.revoked`, `monitoring.policy.within_policy`, `monitoring.policy.escalated` (all added to `LedgerActionType` in the same commit); the dual-control constraint; `standing_policy_scope_is_valid`; `create_standing_policy` (SECURITY DEFINER, service_role only; bounded name/scope, expiry ≤ 365 days, both humans must exist, ledgered as a human action by the author); `revoke_standing_policy` (once, ledgered by the revoker); `evaluate_standing_policy` (the engine, as above).
- **BFF** — `POST /v1/policies/standing` (ESTATE_MANAGE, self-approval 422, expiry window enforced, RPC refusals as 409), `GET /v1/policies/standing` (POSTURE_READ, optional status filter), `POST /v1/policies/standing/:id/revoke` (ESTATE_MANAGE, unknown policy 404), and `POST /v1/plans/:id/standing-approval` (PLAN_APPROVE + kill-switch gate; defaults to the plan's pending actions; the same per-action dry-run/rollback hard gate as the approve route before any digest is computed; signs via the approval engine with the policy's approver; maps decisions — issued 201 with the same signed-token shape the approve route returns and an `approval.pending` broadcast, escalated 200, lapsed/refused 409/422).
- **`fake-postgrest.ts`** unchanged; the route tests seed tables and install RPC handlers.

## Evidence

- **`tests/database/standing-policy-evaluation.test.sql`:** dual control and scope-shape refusals (self-approval, ghost approver, 400-day expiry, empty scope, foreign scope key, zero cap); a within-scope issuance moves the actions and the plan, names the policy's approver on the token with the policy in its conditions, records a `within_policy` evaluation and BOTH ledger entries; escalation by uncovered type and by `max_actions` cap, each recorded and ledgered; the lapsed policy refuses as `policy_expired`, flips itself to `expired` and records the evaluation; revocation lands once, ledgered, and a revoked policy refuses as `policy_revoked` with an evaluation; cross-tenant policy is `policy_not_found`; the gate's own refusals (unsimulated action, drifted digest, stale plan version) produce NO evaluation and NO token; empty/duplicated action ids are `invalid_actions`; `authenticated` cannot execute any of the three functions or write the tables and reads policies only for its own tenant; the (nobypassrls) `service_role` cannot write the tables but can execute the write path.
- **Route tests (`standing-policy.test.ts`, 21):** create with scope bound to another human; capability enforced; self-approval 422; malformed scope/expiry 400 (including the strict-scope foreign-key refusal); RPC refusal 409 and unreachable database 500; list with status filter; revoke and its 404; the evaluate route's issued/escalated/decision-mapping paths, approver identity on the signed spec, pending-actions default, lapsed/expired refusals before evaluation, the dry-run gate (a standing policy does not replace BR-2), stale dry-runs, foreign actions, content-drift 409, gate-refusal 422 with no broadcast, and the kill switch.
- **Results:** BFF 1148 tests pass, types 45, `standing-policy-evaluation.test.sql` and the FULL database suite pass on fresh migrations, typecheck clean, security-scan clean.

## Not delivered

- A monitoring/policy management UI page (the routes are ready for it; W5 web surfaces are in flight separately).
- Alerts/notifications when a policy evaluation escalates (the ledger entry is the signal for now).
- Version bumps as an edit path — deliberately absent: a changed scope is revoke-and-recreate, and the audit trail is the version history.
- Deployed acceptance with a policy issuing a token end-to-end (operator-gated environment).
