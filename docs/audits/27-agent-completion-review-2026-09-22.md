# W4.3 agent completion review — 22 September 2026

The legacy `/v1/agents/:name/run` route awaited a terminal update without inspecting its error or affected row. It then broadcast completion and returned the runtime body. Its response schema accepted any/missing status, arbitrary extra fields and no correlation/agent binding. Runtime-reported failure still received HTTP 200; web callers that accepted the presence of `agent` could report success. Raw runtime/transport errors were saved or logged. This correction is a prerequisite for trustworthy task lifecycle integration.

A dispatched run now retains its owned engagement and exact assigned-input digest. The response must match the assigned agent and correlation, carry a terminal status, bounded database-compatible accounting and explicit output/error/receipt fields. Success requires non-null output, no error and at least two distinct receipt identifiers; the runtime's durable audit adapter remains responsible for those receipts. This route validates their shape, not their authenticity or ledger content. Unknown top-level fields are stripped rather than returned.

The final update uses all context fields and `status=running`, then requests and verifies the affected ID/status. Missing/failed receipts return 503 `agent_completion_unconfirmed`, without output or a completion broadcast. Concurrent cancellation, another terminal state or changed context cannot be overwritten. No automatic re-dispatch or second status update guesses the outcome after an ambiguous commit. The error supplies identifiers for reconciliation.

Authenticated runtime failure, malformed response, non-success HTTP and transport errors return 502 after a confirmed failed invocation row. Only fixed failure codes enter logs/database/client errors; failed output and provider exception details are discarded. Internal-token requests use `redirect: error` and a 120-second deadline. Timeout means dispatch failed to confirm an outcome; it does not prove that an in-flight operation stopped or rolled back. Generic Karya invocation is still forbidden. There is no change to the approved execution endpoint or its 501 runtime stub.

There are 26 new BFF regression cases (572 BFF tests total), including completion persistence failure, concurrent cancellation/terminal/context changes, response identity/status mismatches, contradictory success, missing/duplicate receipts, SQL accounting bounds, response sanitization and raw network/HTTP/JSON failures. The tests exercise the actual Hono route with a stateful PostgREST test double and injected transport. They are not a real isolated-worker or cryptographic delegation acceptance test. Workspace tests/lint/typecheck and repository format/security gates pass. No new migration is required. Cross-layer review also found the new task events absent from the shared TypeScript ledger enum. Both are now included; two additional shared-type tests compare the complete 74-action SQL history with the decoder and reject undeclared action names.

Remaining work is explicit in Docs 11/15/16: production trust delivery, registration lifecycle, separate workers without backend/approval/storage credentials, actual private task orchestration, every-tool scope/data filters and actor-chain verification. The current task authority library is not automatically applied by this legacy route. Saakshi still needs fail-closed metadata persistence and removal of its direct service-role/storage access; runtime adapters must move behind scoped tools. W4.4 grants/approval and full W3 onboarding/graph remain incomplete. Record exact merge CI before treating this correction as a release checkpoint.
