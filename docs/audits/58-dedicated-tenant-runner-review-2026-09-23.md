# Review 58 — dedicated tenant runner deployment foundation

The user explicitly selected a dedicated runner VM per tenant. The previous module created one generic issuer/runner pair for the environment. It now creates one separate issuer plus a tenant-keyed set of runner resources. This is an accepted roadmap refinement, not an accidental deviation or a claim of cloud rollout.

Each runner has its own service account, private address, VM and protected state disk. Controller source ranges belong to individual tenants; per-host firewall resources avoid broad shared target lists. Only the intended runner identity can reach the issuer on TCP8081; its controller remains closed unless its own scheduler ranges are supplied. Baseline denies and HTTPS egress remain, including their existing limitations. UUID-bound labels/metadata/output references support the pending host-placement check. Generated names include a prefix/tenant digest and fit service-account/resource limits; collisions within the module fail a precondition.

Terraform validation and 13 module tests plus eight root tests pass with mocked providers. Tests exercise multiple tenant resources, independent ingress, unchanged default-off behavior, Mumbai placement, private interfaces, state/hardening, key/output bindings and invalid inputs. No cloud API apply, IAM grant, activation or schema change was performed. Mock private addresses do not prove real cloud allocation or effective firewall policy.

Keep the module disabled until supervised startup verifies configured tenant against reviewed host/node references, and backend/secret/KMS/scheduler authorization is validated separately. Dedicated VMs are a placement boundary, not a replacement for task authorization or database scoping. Legacy non-null configuration and populated Terraform state need explicit migration review: the old generic runner is not automatically adopted, moved, relabeled or deleted. Deletion protection and protected state remain intact.
