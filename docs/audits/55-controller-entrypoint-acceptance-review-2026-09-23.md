# Review 55 — actual controller entrypoint acceptance

The existing VM controller probe verified composition, real SPIRE identity, real database persistence and HTTPS while supplying fixture database/KMS/OIDC ports directly. That evidence did not establish that the deployed command could load protected files, reach an HTTPS backend, start its actual listener or stop through its inherited entrypoint. This revision closes that local acceptance gap without relaxing production code.

The new Docker fixture uploads only synthetic credentials and TLS material over private stdin into owner-only files. An internal network connects the controller to a private HTTPS proxy for the isolated real Supabase key-policy read. The proxy rejects and counts all other backend requests, ensuring the test cannot silently conceal an attempted mutation. An explicit pending assessment job remains unclaimed across startup and invalid caller requests. The proxy, uploader and probes are test plumbing; the tested controller uses the image’s existing entrypoint with explicit `--check`/`--serve` arguments and no entrypoint override.

Eight additional assessment outcomes cover protected startup, TLS-host and foreign-node refusal, unsafe file permissions, private listener identity refusal, absence of raw secrets in Docker environment, graceful shutdown and unchanged claims. The local suite has 71 outcomes, retaining the earlier 63. Exact-merge CI must independently verify the expanded artifact. No raw request, token, key or exception diagnostic is emitted; failures carry only a fixed phase label. Cleanup verifies that the fixture’s containers, volume and network are gone.

This is the acceptance image inheriting the production entrypoint, not a deployed production image. Google identity success, actual cloud KMS, effective IAM, GCP attestation and backup/restore remain external gates. Protected host delivery and supervised container lifecycle are next. No new app route, environment parameter, schema or authorization fallback is introduced.
