# Review 60 — reviewed controller supervision and interrupted ownership

The saved draft is reviewed across static installation, startup, Docker confinement, ownership journaling, monitoring, signal delivery and recovery. Runtime profiles bind the tenant to an independently reviewed placement file and HTTPS backend origin. Unit delivery remains disabled and does not reload systemd. Startup runs the existing protected file, live volume and tenant/VM admission, checks the image's immutable ID and production command/environment, writes a durable intent, verifies the created container, persists its exact ID, and repeats admission before start. Docker/systemd restart policies remain disabled. The service's own role, TLS and backend-policy admission remains authoritative; host or Docker activity does not establish readiness.

The review found missing direct confinement tests and a shutdown timing issue: every Docker operation used a namespace query with a possible 40-second systemctl deadline. Namespace discovery now uses a fixed three-second deadline. Docker receives an explicit 90-second default and requested stop timeout for the application's 85-second shutdown allowance; the unit permits 180 seconds. Native dependency-stop acceptance exposed another real lifecycle issue: `KillMode=control-group` delivered SIGTERM to the in-flight systemctl/Docker child as well as the supervisor, turning an orderly stop into a command failure. The unit now uses `KillMode=mixed`: SIGTERM reaches the supervising main process, its bounded child operations can complete, and systemd still kills the whole group at the stop deadline. Recovery still fails closed if the daemon cannot be observed or an owned stop cannot be confirmed. It cannot make host/disk loss transparent, and it must not relaunch a job to hide uncertainty.

A second recovery race was found: after a timed-out start request, Docker may still report created while activation is in flight. The supervisor now persists a start intent before the request. A created object with that intent cannot receive a stopped receipt or permit another lifetime; eventual running/exited state must first be observed and owned shutdown confirmed. Both unit and native fixture regressions cover this boundary.

Confinement now directly checks the stop timeout, runtime, user namespace, automatic removal, wildcard publishing and OOM behavior, and rejects unsolicited device rules, sysctls, storage/cgroup/DNS overrides in addition to the earlier checks. UID 20000, private bridge/IP/8443, read-only root/files/volumes, private IPC/cgroup, dropped capabilities, no-new-privileges and bounded memory/PIDs are preserved. The daemon socket is available only to the trusted controller. Root and daemon access remain trusted host authority; these controls are not a sandbox against a compromised daemon administrator.

The saved Docker Desktop probe's mismatch was reproduced with a minimal create-only command using the existing controller image: the requested `10.0.0.11:8443:8443/tcp` returned `127.0.0.1` and an empty host port. This demonstrates a local daemon-path mismatch independently of the runtime argument builder, but does not establish its deeper Desktop cause. Nothing was started, and the probe's exact created ID was removed. The production validator continues to refuse the observation. Native hosted Ubuntu subsequently confirmed the requested private-IP/fixed-port representation. Its mount check exposed an empty `DriverConfig: {}` emitted by the native client for each otherwise identical volume. Normalization accepts only that empty object as equivalent to an unspecified driver; nonempty/unknown driver fields, changed source/target/read-only flags and disabled NoCopy remain refused. Direct regressions cover both forms. The initial failed native runs are diagnostic evidence, not closure evidence.

Recovery requires a private per-tenant lock and journal, exact full ID/name/image/labels, and matching profile/attempt/tenant bindings. It uses no metadata, issuer, backend, DNS or KMS call. ID persistence failure or uncertain creation leaves only intent and prohibits start or name adoption. A stop timeout leaves an unresolved receipt; only an explicit verified retry can complete it. No container deletion, job reset, credential repair or cloud provisioning exists in this helper. Stopped container/journal retirement remains an explicit operator concern, separate from configurable completed-dispatch retention.

Validation: 165 deployment tests pass, including 24 controller runtime tests. Direct field-mutation checks cover the confinement validator; failure tests cover create uncertainty, changed admission, signal during creation, failed ID persistence, start uncertainty, stop timeout, foreign ownership and corrupted intent. Workspace tests, lint, typecheck, formatting and security/control gates pass locally. The native fixture adds twelve intended outcomes to the prior 33: installation/idempotence and conflict refusal, production local-node rejection, confinement/graceful stop, competing start, unexpected exit, foreign-ID refusal, explicit recovery, wrapper death, dependency loss, uncertain start and uncertain creation. Final native counts and exact source/merge CI require the artifacts recorded in Doc 15.

The native process is deliberately synthetic and its wrapper substitutes only local-node placement. It is not the production controller, GCP attestation or a cloud deployment. Separate actual production-entrypoint, identity and 71-outcome assessment acceptance remain required. Effective tenant-scoped backend/secret/IAM/KMS permissions, real private TLS/DNS, opaque scheduler deployment, valid cloud caller/KMS identity and Mumbai backup/restore remain open. Application approval/dry-run/rollback, Sudhaar separation, append-only ledger, WORM and locality are unchanged.
