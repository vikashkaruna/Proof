# Approval proof archive (W8.5)

This workflow turns a completed approval and execution into a source-bound, independently retained JSON proof. Migration `0090_approval_proof_archive.sql` is additive. Historical approval exports remain explicitly unverified; they gain an `archived_proof` reference only after the new proof is released.

## What the proof binds

`prepare_plan_reconciliation` constructs the exact statement Samadhan signs. It includes the approved token and content digest, the execution batch, action outcomes, unexecuted work, verification records and any drift. `record_plan_reconciliation` accepts only that byte-exact statement **and verifies its HMAC inside the insert/ledger transaction**. The Python producer signs it with its configured approval signing key and refuses to run without a key. A missing or mismatched database verifier key returns `reconciliation_signature_unverified` before a row or success ledger event is written. No default/fallback key is used by the producer.

Samadhan derives its database-backed verdict from the signed statement, treats a failed verification as incomplete execution, and marks the result `source_bound` in output details. A local helper call without a database may still return a diagnostic signed statement, but its details say `source_bound: false`; it cannot be recorded or archived as the maker-checker proof. A database refusal cannot fall back to that diagnostic path.

`prepare_approval_proof_source` reconstructs the archive bytes from the stored token and issuance ledger, completed dry-run with matching parameter and rollback hashes, validated rollback flag, completed execution batch, verification records, signed reconciliation and reconciliation ledger. It rejects missing or inconsistent links, including a pre-repair reconciliation with a hex-shaped but forged signature. The BFF also verifies both the approval token signature and the reconciliation HMAC with the tenant's approval key before beginning retention. Pramaan refuses supplied reconciliation statements whose HMAC or tenant/batch source binding fails, and a row ID alone cannot establish maker-checker proof. The database refuses tokens whose stored scope, conditions or expiry disagree with the signed payload. Existing unsigned conditions do not become signed facts by export.

The resulting JSON records stored facts and their provenance. It does not assert that an older historical export was verified. Human approval, Samadhan reconciliation and founder release are distinct actions; all archive transitions append ledger entries in the same database transaction.

## Retention and release

An internal founder opens an archive from a consumed token on the plan page or through `POST /v1/approvals/:tokenId/archive` with a UUID `operationKey`. The BFF freezes the exact source hash and bytes in a pending intent before a create-only provider PUT. A provider timeout leaves the intent pending. Repeating `start` cannot cause a second PUT. The founder can call `POST /v1/approval-archives/:id/reconcile` to read back an already written version, or `POST /:id/retry-missing` after the exact operation's version is confirmed absent.

Settlement requires readback of the exact bucket, key, object version, byte count, SHA-256, operation ID and tenant metadata, together with Compliance Object Lock retention and encryption. The version receipt is immutable. A founder opens `GET /v1/approval-archives/:id/preview` to see the retrieved, hash-checked exact retained source, then explicitly records review with its source hash and version at `POST /v1/approval-archives/:id/review`. The review row and ledger entry are append-only. `POST /v1/approval-archives/:id/release` refuses a missing or mismatched review and rechecks the current source, signatures and provider version before founder release. A released version is downloadable by an export-capable tenant member at `GET /v1/approval-archives/:id/download`; the BFF retrieves that version ID and checks its bytes and hash. Pending and settled records remain founder-only. Viewer access is refused.

`GET /v1/approvals/:tokenId/archive` returns the current permitted status for the plan UI. The UI describes pending, settled and released states separately, includes explicit recovery controls, and never presents an unretained historical export as sealed proof.

## Operating limits and key alignment

The DB-computed signed statement is bounded to 256 KiB and the retained source to 4 MiB. Oversized or incomplete chains are refused for investigation; no truncated proof is emitted. The verifier key lives in `axiom_secrets.reconciliation_keys`; `service_role` has no schema or table access. The migration does not seed a key. `scripts/migrate-cloudsql.sh` provisions the shared key from its existing `APPROVAL_SIGNING_KEY` environment through a DB-admin connection and fails a preprod/production migration without it. For a tenant-specific signer, run `scripts/provision-reconciliation-key.py --tenant-id <tenant UUID>` with that tenant's `APPROVAL_SIGNING_KEY` and `SUPABASE_DB_URL` injected from the secret manager into the process environment. The command refuses an existing different key; no key or database password is placed in its argv or output. The tenant key must match both Samadhan and BFF. A mismatch fails closed. Rotation is deliberately blocked by the provisioner until a trusted historical verification-key ring exists in the database and BFF; replacing a key in place would make old retained HMAC tokens unverifiable.

Reconciliation events written before this repair remain in the append-only ledger. Their old `recorded` label is historical, not proof of signature verification. Consumers must require a valid HMAC under the protected key and cannot rely on that event or a 64-character signature alone. Suspect pre-repair rows require operator investigation and an appended correction; the ledger must not be edited or deleted.

The local provider browser journey uses synthetic personas and an owned loopback Object Lock fixture. It is not evidence of a cloud or production retention configuration. Production acceptance still requires the target-specific gates in [the deployment and acceptance guide](18_Operator_Deploy_And_Acceptance.md).
